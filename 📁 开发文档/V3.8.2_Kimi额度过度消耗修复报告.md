# V3.8.2 → V3.8.3: Kimi API 额度过度消耗 — 根因分析与修复

> 日期: 2026-02-14
> 问题: Kimi K2.5 API 每隔 3-6 秒被调用，额度快速耗尽
> 状态: **已修复并验证通过**

---

## 一、问题现象

- Gateway 日志显示每 60-90 秒生成新信号，路由到 1-3 个 agent
- trader agent 累积 19 个活跃 session（15 hook + 3 discord + 1 main）
- 每个 session 都在消费 Kimi API，导致每 3-6 秒一次调用
- V3.8.1 的限流措施（max_turns=2, budget=3）效果不足

---

## 二、根因分析（三层问题）

### Layer 1: Realtime Engine 旁路 PG 轮询（核心根因，占 60%）

```
data-service 写入 → PostgreSQL NOTIFY → realtime_engine LISTEN
→ 直接调用 pg_engine.check_signals() → 绕过 PG 300s 轮询间隔
```

`realtime_engine.py` 的 `create_realtime_signal_checker()` 在每次收到 NOTIFY 时**无限流地**调用 `pg_engine.check_signals()`。1m K线每分钟触发一次，5m 指标每 5 分钟触发一次，完全绕过了 PG Engine 的轮询间隔。

### Layer 2: PG Edge 检测振荡重触发（占 25%）

PG Engine 使用 `_prev_active` set 做边缘检测：信号只在 inactive→active 转换时触发。但当指标在阈值附近振荡时：

```
t=0s:  taker_ratio=0.52 → active → FIRE signal
t=60s: taker_ratio=0.49 → inactive (边缘清除)
t=120s: taker_ratio=0.51 → active → FIRE signal (又一次!)
```

Gateway 日志实证：信号状态在 12-89 秒内就被清除并可再次触发。

### Layer 3: 多 Agent 路由放大效应（占 15%）

每个信号通过 signal-router.js 路由时：
- 可能触发 MULTI_ROUTE_RULES 发给 2-3 个 agent
- 每个 agent 创建独立 hook session
- 每个 session 消费 max_turns 次 Kimi API

单个信号最多产生 3 agents × 6 turns = 18 次 API 调用。

---

## 三、V3.8.2 修复（止血 — 三层限流）

### Layer 1: Realtime Engine 限流

**文件**: `services/signal-service/src/engines/realtime_engine.py`

```python
# V3.8.2: 限流 -- 最多每 300s 触发一次信号检查
_last_check_time = [0.0]
_MIN_CHECK_INTERVAL = 300  # 与 PG 轮询间隔一致

def _throttled_check(trigger_type, symbols):
    now = time.time()
    elapsed = now - _last_check_time[0]
    if elapsed < _MIN_CHECK_INTERVAL:
        return  # 限流跳过
    _last_check_time[0] = now
    signals = pg_engine.check_signals()
```

### Layer 2: PG Edge 最小触发间隔

**文件**: `services/signal-service/src/engines/pg_engine.py`

```python
# V3.8.2: 边缘触发时间记录 -- 即使状态重置，同一信号 10 分钟内不重复触发
self._edge_fire_times: dict[str, float] = {}
self._edge_min_interval = 600  # 10 分钟最小间隔
```

### Layer 3: PG 轮询间隔 + 信号冷却

**文件**: `services/signal-service/src/__main__.py`
- PG 轮询间隔: 60s → 300s

**文件**: `services/signal-service/src/config.py`
- `COOLDOWN_SECONDS`: 300 → 900（同一信号 15 分钟冷却）

### 验证结果 (V3.8.2)

5 分钟综合监控：
- Signal Service: 仅 1 个信号生成，其余被限流
- Gateway: **零** Router 处理
- 所有 agent: **0 sessions**
- Kimi API 调用: **完全停止**

## 四、V3.8.3 参数回调（恢复交易能力）

> V3.8.2 止血成功，但过度限流导致 **agent 丧失交易能力**

### 问题: max_turns=2 硬编码

V3.8.1 将三个路由函数的 `max_turns` 从 6 硬编码为 2，导致：
- `applyTurnsOptimization()` 函数完全失效（基础已是 2，优化也是 2）
- Agent 只有 2 轮对话，只够做分析
- 完整交易流程需要 4+ 轮: **分析 → 计算仓位 → 下单 → 写笔记**

### V3.8.3 修改清单

**文件**: `openclaw-config/transforms/signal-router.js`

| 参数 | V3.8.1 | V3.8.2 | V3.8.3 | 说明 |
|------|--------|--------|--------|------|
| max_turns (base) | 2 | 2 | **4** | 恢复完整交易流程 |
| max_turns (can_trade=false) | 2 | 2 | **2** | 仅分析模式保持节省 |
| ttl_minutes | 3 | 3 | **5** | 给 4 轮留足时间 |
| SESSION_BUDGET_MAX | 3 | 1 | **2**/10min | 适度放宽 |
| DEDUP_WINDOW_MS | 30min | 60min | **30min** | 回调到合理值 |
| REJECTION_COOLDOWN_MS | 60min | 2hr | **60min** | 回调到合理值 |

### 修复后的 `applyTurnsOptimization` 逻辑

```javascript
function applyTurnsOptimization(routeResult, canTrade) {
  if (!canTrade) {
    routeResult.session_config.max_turns = 2;   // 仅分析
    routeResult.session_config.ttl_minutes = 3;
  }
  // can_trade=true 时保持 base: max_turns=4, ttl=5min
}
```

### API 调用量估算

**修复前 (V3.8.0)**:
- 信号频率: ~1 个/分钟
- 路由放大: 1-3 agents
- 每 session: 6 turns
- 预估: 6-18 次 API 调用/分钟 → **360-1080 次/小时**

**修复后 (V3.8.3)**:
- 信号频率: ~1 个/5分钟（PG 300s + Realtime 300s 限流）
- 路由: 最多 2 sessions/10min（Budget 限制）
- 每 session: 2-4 turns
- 预估: 4-8 次 API 调用/10分钟 → **24-48 次/小时**

**降幅: ~95%**

## 七、后续优化方向

1. **Discord WebSocket 重连**: 持续 code 1005/1006 循环（每 20-40 秒），不消耗 Kimi API 但增加日志噪声
2. **signal-router.js 重复函数**: `getStrategyEvolution` 定义了两次（第 232-244 行和第 249-261 行），应删除第一个
3. **Realtime Engine 可考虑放宽**: `_MIN_CHECK_INTERVAL` 300→180s，让实时引擎比 PG 轮询稍快，提升信号时效性
4. **进化数据清洗**: `*_evolution.json` 的 `net_profit` 混合了百分比和 USDT 两种单位

## 八、关键教训

1. **LISTEN/NOTIFY 不等于轮询替代** — 必须在回调中添加独立限流，否则会绕过所有上层控制
2. **边缘检测 + 振荡 = 频繁触发** — 仅依赖状态转换不够，需要时间维度的最小间隔
3. **紧急限流后必须回调** — V3.8.1 的 max_turns=2 作为止血措施有效，但遗忘回调会导致系统丧失核心功能
4. **根源修复优于症状限流** — 在源头控制信号频率（300s PG + 300s Realtime + 600s Edge），比在路由层层加限更可靠、更简单
