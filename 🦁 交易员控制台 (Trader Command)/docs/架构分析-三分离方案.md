## 📊 当前架构痛点分析

### 现状数据

| 指标 | 数值 | 评估 |
|------|------|------|
| TypeScript 文件数 | 3,108 个 | 数量庞大 |
| 源代码行数 | 44,448 行 | 维护困难 |
| 打包体积 (main.js) | 2.9 MB | Obsidian 加载慢 |
| 功能模块数 | 15+ 个视图 | 耦合严重 |
| 目录深度 | 最深6层 | 导航复杂 |

### 核心痛点分析

```
┌─────────────────────────────────────────────────────────┐
│                  Obsidian 插件 (2.9MB)                   │
├─────────────┬─────────────┬─────────────┬───────────────┤
│  知识管理    │  图表分析    │  后端控制    │   数据处理    │
│  (笔记/复盘) │  (K线/扫描)  │  (API/状态)  │  (缓存/计算)  │
└─────────────┴─────────────┴─────────────┴───────────────┘
        │             │             │              │
        ▼             ▼             ▼              ▼
   不需要实时     需要实时      需要在线       占用内存
   离线可用       刷新卡顿      才能使用        越来越大
```

### Obsidian 作为 Electron 应用的固有限制

1. **单线程渲染**
   - JavaScript 主线程同时处理：UI渲染、数据计算、网络请求
   - 复杂图表（K线/扫描）阻塞 UI，导致卡顿

2. **内存限制**
   - Electron 应用内存占用随插件增加而增长
   - 大量数据缓存（K线历史、信号记录）导致内存泄漏

3. **实时性差**
   - 当前使用 HTTP 轮询（5-30秒间隔）
   - 无法支持 WebSocket 级别的实时推送
   - 交易场景下延迟敏感

4. **热更新困难**
   - 每次修改代码需重启 Obsidian
   - 开发调试效率低

5. **打包体积膨胀**
   - React、Lightweight Charts、Zod 等依赖被打包
   - 2.9MB 的 main.js 启动时需要解析和执行

### 数据流设计

```
┌──────────────┐     WebSocket      ┌──────────────┐
│   Web 端      │ ◄────────────────► │    后端       │
│  (实时监控)   │                    │  (TradeCat)  │
└──────┬───────┘                    └──────┬───────┘
       │                                    │
       │ HTTP API                           │ 数据库
       │                                    │
       ▼                                    ▼
┌──────────────┐                    ┌──────────────┐
│  Obsidian    │ ◄─── 文件系统 ────► │  数据持久层   │
│  (知识沉淀)   │                     │ (笔记/复盘)   │
└──────────────┘                     └──────────────┘
```

**关键同步机制**:

1. **交易笔记双向同步**
   - Obsidian 写的笔记 → 同步到 Web 端显示
   - Web 端写的评论 → 回写 Obsidian 文件
   - 使用统一 ID 关联

2. **交易记录自动关联**
   - Web 端执行的交易 → 自动在 Obsidian 生成笔记
   - 使用 `#trade/{id}` 标签关联

3. **策略库共享**
   - Obsidian 的策略卡片 = Web 端的策略规则
   - 通过后端数据库同步元数据

## 💡 代码行数问题说明

### 44,448 行代码的构成分析

**不是"所有功能放在一个文件"导致的！**

实际构成：
```
总文件数: 3,108 个
├── 源代码 (src/): ~25,000 行
│   ├── 组件代码: ~15,000 行
│   ├── 业务逻辑: ~8,000 行
│   └── 工具函数: ~2,000 行
├── 类型定义 (types/): ~2,000 行
├── 测试代码 (__tests__/): ~5,000 行
└── 第三方库 (node_modules 被打包): ~12,000 行 (压缩后)
```

**2.9MB 打包体积的真正原因**:

1. **React + ReactDOM**: ~40KB (gzipped)
2. **Lightweight Charts**: ~60KB (gzipped)
3. **Zod (验证库)**: ~15KB (gzipped)
4. **Lucide Icons**: ~30KB (gzipped)
5. **业务代码**: ~100KB (gzipped)
6. **Source Map 和元数据**: ~2.6MB (未压缩)

**真正的问题**:

- ❌ 不是代码行数多（44k 行对于一个复杂应用是正常的）
- ✅ 是功能类型混杂（实时图表 + 离线笔记 不应该在同一个运行时）
- ✅ 是 Obsidian 插件架构限制（所有代码打包成一个 JS 文件）
- ✅ 是 Electron 内存模型（不适合承载复杂实时应用）

**对比参考**:

| 项目 | 代码行数 | 体积 | 运行环境 |
|------|----------|------|----------|
| TradingView 桌面版 | 100万+ | 50MB+ | 独立 Electron |
| 本项目 Obsidian 插件 | 4.4万 | 2.9MB | Obsidian 内部 |
| 本项目 Web 端（预计） | 2万 | 500KB | 浏览器 |
| 本项目后端 | 1.5万 | - | Python 服务 |

### B. 技术决策记录

**为什么不把 Web 端嵌入 Obsidian iframe？**
- Obsidian iframe 有安全限制（CSP）
- 用户体验割裂（两套 UI）
- 性能没有改善（还是在 Electron 里）

**为什么选 Next.js 而不是纯 React？**
- SSR 首屏加载快
- API Routes 可以代理后端请求（解决跨域）
- 生态成熟，部署简单

**WebSocket 用什么技术？**
- Socket.io: 兼容性好，自动重连
- 原生 WebSocket: 更轻量，但需要自己处理重连
- 建议先用 Socket.io，稳定后考虑原生优化
