## 1. 项目概述与背景

### 1.1 当前系统能力

AB Console 是一套围绕 Al Brooks 价格行为学 (Price Action) 构建的完整交易系统，包含三大子系统：

| 子系统 | 技术栈 | 核心功能 |
|--------|--------|----------|
| **AB Console-Backend** | Python 微服务架构 | 6 个微服务：行情同步、信号检测、交易管理、AI 分析、Telegram 推送 |
| **AB Console-Obsidian** | Obsidian Vault + 自研插件 | 2600+ 笔记（53 课视频字幕 + 形态笔记 + 交易日志），al-brooks-console 插件 |
| **AB Console-Web** | Next.js (port 3000) | 市场扫描仪表盘、策略匹配、信号可视化 |

当前系统已经具备了从数据采集到信号推送的完整链路：

```
币安 API → data-service → signal-service (129 规则) → telegram-service → 用户
                ↓
          trading-service (34 指标) → api-service:8088 → Web Dashboard:3000
```

### 1.2 为什么需要 CLAWDBOT 集成

**核心痛点**：现有 Telegram Bot 的 AI 分析能力严重不足。

用户原话描述为"很呆"——Bot 只能报数字（价格、指标值、信号名称），缺乏对价格行为的深层理解。具体表现为：

1. **无法进行 Context 分析**：信号检测基于规则引擎（129 条规则），但无法像 Al Brooks 那样综合判断"市场周期 + 信号质量 + 概率"的三维关系
2. **无法给出交易指导**：只告知"出现 H2 信号"，但不能评估该信号在当前 context 下是否值得交易
3. **缺少实时交互**：单向推送，无法进行问答式的盘中讨论
4. **无复盘能力**：无法在盘后结合 Al Brooks 原则对交易进行归因分析
5. **知识库断裂**：Obsidian 中 2600+ 笔记的知识完全无法被 Bot 利用

**CLAWDBOT 集成目标**：将 LLM 的自然语言理解与推理能力引入交易流程，构建一个"AI 版 Al Brooks"，实现：

- 实时价格行为解读（不只是数字，而是"这是宽通道中的 H2 回调，概率偏向继续"）
- 交易决策辅助（盈亏比计算、概率评估、入场/止损/止盈建议）
- 盘后复盘与学习指导
- 知识库的智能检索与引用

## 2. 现有系统分析

### 2.1 后端微服务清单

AB Console-Backend 采用 Python 微服务架构，通过 Docker Compose 编排，包含以下 6 个核心服务（另有 1 个 API 网关）：

| 服务 | 端口 | 职责 | 关键数据 |
|------|------|------|----------|
| **api-service** | 8088 | REST API 网关，对外统一接口 | 聚合所有服务数据，提供 HTTP 端点 |
| **sync-service** | 8089 | 数据同步，对接币安 API | K 线数据、订单簿、Ticker |
| **signal-service** | 内部 | 信号检测引擎，129 条规则 | 形态信号、入场点、置信度 |
| **data-service** | 内部 | 数据存储与查询 | 历史 K 线、指标计算结果 |
| **trading-service** | 内部 | 交易管理，34 个技术指标 | 持仓状态、订单、盈亏记录 |
| **telegram-service** | 内部 | Telegram Bot 消息收发 | 消息队列、用户会话 |
| **ai-service** | 内部 | 现有 AI 分析（功能有限） | AI 生成的分析文本 |

**服务间通信**：内部服务通过 HTTP 或消息队列通信，api-service 作为唯一对外网关。

                    │                                                     │
                    │  signal-service                                     │

### 2.3 Obsidian Vault 的角色

AB Console-Obsidian 是整个系统的**知识中枢**，包含：

| 内容类型 | 数量 | 说明 |
|----------|------|------|
| 视频字幕笔记 | 53 课 (01-53) | Al Brooks 完整课程，已修复格式（40 课已完成） |
| 形态与结构笔记 | 数百篇 | 覆盖 14-21 课对应的突破、缺口、趋势、反转、楔形、双顶底、三角形等 |
| 标签系统 | 30+ 标签目录 | `#pa+term+breakout`、`#pa+strategy+gap-trading` 等结构化标签 |
| 交易日志 | 持续增长 | 通过 al-brooks-console 插件记录的实盘/模拟交易 |
| JournalIt 缓存 | trade-cache.json | 交易记录的本地缓存 |

**当前问题**：这些知识完全是离线的，只能通过人工翻阅 Obsidian 获取。没有任何 API 或搜索接口可供外部系统调用。

### 2.4 Web Dashboard 能力

Next.js 仪表盘 (port 3000) 提供：

- **市场扫描**：多品种实时行情概览
- **策略匹配**：基于当前行情匹配 Al Brooks 策略（已发现字段映射 bug，见第 5 节）
- **信号可视化**：signal-service 检测结果的图形化展示
- **交易管理**：持仓、历史记录查看

### 2.5 现有 Telegram Bot 的局限性

telegram-service 当前的 AI 能力由 ai-service 提供，存在以下问题：

| 局限 | 详情 |
|------|------|
| **分析深度不足** | 只报数字和信号名称，缺乏价格行为解读 |
| **无 Context 意识** | 不考虑市场周期、不评估信号在当前环境下的质量 |
| **单向推送** | 用户无法追问"为什么"或"应该怎么做" |
| **无状态** | 不记录交易过程，无法跟踪从开仓到平仓的完整生命周期 |
| **知识孤岛** | 完全不利用 Obsidian 中 2600+ 笔记的知识 |

### 3.3 当前存在的问题

#### 问题 1: SKILL.md 体积过大 (17K tokens)

CLAWDBOT 每次对话都需要加载完整 SKILL.md 作为系统提示词。17K tokens 意味着：

- 占用大量上下文窗口（以 128K 上下文的模型为例，仅系统提示就占 13%）
- 每次 API 调用都要发送全部内容，增加延迟和成本
- 实际对话可用空间被压缩，影响长对话质量

**合理范围**：系统提示词应控制在 5K-8K tokens 以内。

#### 问题 2: 内容重叠率超过 40%

经过对比分析，SKILL.md 与 references/ 和 knowledge/ 目录的内容重叠极为严重：

```
SKILL.md 中的策略内容 ≈ references/14-strategies.md
SKILL.md 中的概率数据 ≈ references/15-probability.md ≈ knowledge/probability-cheatsheet.md
SKILL.md 中的核心概念 ≈ references/00-core-concepts.md ≈ knowledge/core-concepts.md
SKILL.md 中的决策流程 ≈ knowledge/trading-decision-flow.md
```

这意味着至少 40% 的 SKILL.md 内容可以通过引用外部文件替代，而非内嵌在系统提示词中。

#### 问题 3: 无动态加载机制

当前设计是"一次性全量加载"模式。理想做法是：

- **核心提示词**（身份 + 行为准则 + 输出格式）：始终加载
- **知识参考**（策略、概率、术语）：按需加载（用户问到策略时才加载策略文件）
- **实时数据**（市场行情、信号）：通过工具调用获取

CLAWDBOT 的 Skill 系统支持 `references/` 目录的按需引用，但当前 SKILL.md 已经内嵌了所有 reference 内容，使得外部文件形同虚设。

#### 问题 4: 实战案例硬编码

SKILL.md 中的实战案例是静态文本，存在以下问题：

- 案例无法随交易经验积累而自动更新
- 案例数量有限，无法覆盖各种市场情境
- 理想方案是从交易日志中动态检索相似案例

## 4. 集成方案评估

### 4.1 方案 A: API 直连

```
┌──────────────┐    HTTP/REST    ┌──────────────┐    内部调用    ┌──────────────┐
│  CLAWDBOT    │ ──────────────→ │ api-service  │ ────────────→ │  各微服务     │
│  (AI Core)   │                 │   :8088      │               │              │
└──────────────┘                 └──────────────┘               └──────────────┘
```

**实现方式**：在 CLAWDBOT Skill 中配置 HTTP 工具，直接调用 api-service 的 REST 端点。

| 维度 | 评估 |
|------|------|
| **实现周期** | 1 周 |
| **技术复杂度** | 低 |
| **安全性** | 差 -- API Key 需要暴露给 CLAWDBOT 平台 |
| **扩展性** | 差 -- 每增加一个端点都需要修改 Skill 配置 |
| **实时性** | 单向（CLAWDBOT 主动拉取），无法接收推送 |
| **上下文管理** | 无 -- 每次调用独立，不维护交易会话状态 |

**优点**：
- 实现最简单，可在 1 周内完成 MVP
- 不需要额外的基础设施
- 直接复用现有 api-service 端点

**缺点**：
- 紧耦合：CLAWDBOT 需要知道每个 API 的 URL、参数格式、认证方式
- 安全风险：API 凭据需要配置在 CLAWDBOT 平台上
- 无法推送：signal-service 检测到高概率信号时，无法主动通知 CLAWDBOT
- 无能力发现：新增 API 端点后，需要手动更新 Skill 配置

**适用场景**：快速验证"LLM + 交易数据"的分析效果是否达到预期。

### 4.2 方案 B: MCP 协议 (推荐)

```
┌──────────────┐   MCP Protocol   ┌──────────────┐   内部调用   ┌──────────────┐
│  CLAWDBOT    │ ←──────────────→ │  MCP Server  │ ───────────→ │  各微服务     │
│  (AI Core)   │   (双向通信)      │  (Gateway)   │              │              │
└──────────────┘                  └──────────────┘              └──────────────┘
```

**实现方式**：开发一个 MCP Server 作为 CLAWDBOT 与后端之间的标准化网关。

**MCP Server 提供的 Tools**：

```typescript
// 市场数据类
analyze_market(symbol, timeframe)     // 获取行情 + 指标 + AI 分析
get_kline_data(symbol, timeframe, limit) // 获取原始 K 线数据
get_indicators(symbol, timeframe)     // 获取 34 项技术指标

// 信号类
get_signals(symbol?, timeframe?)      // 获取当前信号检测结果
get_signal_history(symbol, days)      // 获取历史信号

// 交易类 (只读)
get_positions()                       // 获取当前持仓
get_trade_history(symbol?, days?)     // 获取交易历史
check_setup(plan)                     // 审核交易计划的风险收益比

// 知识库类
search_knowledge(query)               // 向量检索 Obsidian 笔记
get_strategy(strategy_name)           // 获取策略详情
get_probability(pattern_name)         // 获取概率数据

// 日志类
update_journal(entry)                 // 更新交易日记 (写入 Obsidian)
```

| 维度 | 评估 |
|------|------|
| **实现周期** | 2-3 周 |
| **技术复杂度** | 中 |
| **安全性** | 好 -- 凭据在 Server 端管理，CLAWDBOT 不接触 |
| **扩展性** | 好 -- 新增 Tool 只需在 MCP Server 注册 |
| **实时性** | 双向（MCP 协议支持 Server 主动推送通知） |
| **上下文管理** | 可通过 MCP Resources 提供上下文 |

**优点**：
- 标准化协议，CLAWDBOT 原生支持 MCP
- 安全隔离：所有 API Key、数据库连接字符串都在 MCP Server 端
- 能力自动发现：CLAWDBOT 可以自动发现 MCP Server 提供的所有 Tools
- 双向通信：signal-service 的高概率信号可以通过 MCP 推送到 CLAWDBOT
- 权限控制：可以在 MCP Server 层面实现只读/读写权限分离

**缺点**：
- 需要开发 MCP Server（Python 或 Node.js）
- 需要理解 MCP 协议规范
- 调试链路变长（CLAWDBOT -> MCP -> api-service -> 微服务）

**适用场景**：中期目标，在 MVP 验证通过后实施。

### 4.3 方案 C: 混合架构 (最终形态)

```
┌───────────────────────────────────────────────────────────────────────────┐
│                           用户交互层                                      │
│    Telegram / Web Dashboard / CLAWDBOT 直接对话                           │
└────────────────────────────┬──────────────────────────────────────────────┘
                             │
┌────────────────────────────▼──────────────────────────────────────────────┐
│                         协议路由层                                        │
│                                                                          │
│   ┌────────────┐   ┌────────────────┐   ┌──────────────────┐            │
│   │ MCP (读取)  │   │ REST API (写入) │   │ WebSocket (实时)  │            │
│   │ 行情查询    │   │ 下单/止损       │   │ 信号推送          │            │
│   │ 信号检索    │   │ 日志写入       │   │ 价格提醒          │            │
│   │ 知识搜索    │   │ 配置修改       │   │ 状态变更          │            │
│   └─────┬──────┘   └───────┬────────┘   └────────┬─────────┘            │
│         │                  │                      │                      │
│   ┌─────▼──────────────────▼──────────────────────▼─────────┐            │
│   │                    MCP Gateway Server                    │            │
│   │    统一鉴权 / 速率限制 / 日志审计 / 读写分离              │            │
│   └─────────────────────────┬────────────────────────────────┘            │
└─────────────────────────────┼────────────────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────────────────┐
│                         后端服务层                                        │
│   api-service / data-service / signal-service / trading-service          │
│   sync-service / telegram-service / ai-service                           │
└──────────────────────────────────────────────────────────────────────────┘
```

**协议分工**：

| 协议 | 用途 | 方向 | 延迟要求 |
|------|------|------|----------|
| **MCP Tools** | 数据查询、知识检索、分析请求 | CLAWDBOT -> Backend | 中 (1-5s) |
| **REST API** | 交易执行、日志写入、配置修改 | CLAWDBOT -> Backend | 低 (<1s) |
| **WebSocket** | 实时信号推送、价格提醒、状态变更 | Backend -> CLAWDBOT | 极低 (<100ms) |

**优点**：
- 每种协议用在最合适的场景
- 读写分离，安全性最高
- 实时推送能力，signal-service 检测到信号后可即时通知
- 可以实现完整的"实时陪练 + 提醒 + 复盘"三种模式

**缺点**：
- 实现复杂度最高
- 需要维护三种协议的集成
- 调试和监控成本增加

**适用场景**：长期目标，在 MCP 方案稳定运行后逐步演进。

## 5. 关键问题识别

通过对现有代码、文档、架构的全面分析，识别出以下 7 个必须解决的关键问题：

### 5.1 实时性与延迟问题

**问题描述**：

LLM 推理耗时在 2-10 秒之间，叠加 API 调用延迟，整个分析链路可能需要 5-15 秒。而在 Spike（急速）行情阶段，价格可能在数秒内剧烈波动。

```
用户请求 → CLAWDBOT 接收 → MCP 调用 → api-service → signal-service → 返回数据 → LLM 推理 → 输出
   0s          0.5s          1s         1.5s          2s             3s         5-10s      10-15s
```

**对交易的影响**：

| 行情阶段 | 价格变化速度 | 15 秒延迟的影响 |
|----------|------------|---------------|
| Spike（急速） | 极快 | **致命** -- 入场点已过 |
| 紧通道 | 快 | **严重** -- 可能错过最佳 tick |
| 宽通道 | 中等 | **可接受** -- 有足够的回调空间 |
| 交易区间 | 慢 | **无影响** -- 价格反复 |

**解决方案**：明确分工，分离"主动分析"和"被动提醒"两条链路。

```
链路 1 (被动提醒 -- 低延迟):
  signal-service 检测到信号 → telegram-service 直接推送 → 用户手机
  延迟: <2 秒
  适用: Spike 阶段、止损触发、突破确认

链路 2 (主动分析 -- 高延迟可接受):
  用户提问 → CLAWDBOT → MCP → 后端 → LLM 分析 → 输出
  延迟: 5-15 秒
  适用: 宽通道回调、交易区间、盘后复盘
```

关键原则：**不要用 CLAWDBOT 替代 signal-service 的实时提醒功能，而是让两者各司其职。**

---

### 5.2 CLAWDBOT 与现有 Telegram Bot 的职责边界

**问题描述**：

系统中将同时存在两个"AI 交互入口"：CLAWDBOT 和现有的 Telegram Bot（由 telegram-service 驱动）。如果不明确边界，将导致：
- 用户困惑：该问谁？
- 功能重复：两个 Bot 都在推信号
- 资源浪费：相同的分析跑两遍

**解决方案**：明确分工矩阵。

| 功能 | 现有 Telegram Bot | CLAWDBOT |
|------|-------------------|----------|
| 信号提醒（"BTC 出现 H2"） | 主要负责 | 不负责 |
| 价格到达提醒 | 主要负责 | 不负责 |
| 止损触发提醒 | 主要负责 | 不负责 |
| 深度分析（"当前 BTC 该怎么看"） | 不负责 | **主要负责** |
| 交易计划审核 | 不负责 | **主要负责** |
| 盘后复盘 | 不负责 | **主要负责** |
| 学习指导 | 不负责 | **主要负责** |
| 互动问答 | 简单关键词回复 | **自然语言对话** |

**技术实现**：
- Telegram Bot 保持现有逻辑不变，作为"快速提醒频道"
- CLAWDBOT 通过 MCP 接入后端数据，作为"深度分析顾问"
- 两者通过 api-service 共享数据，但不互相调用

### 5.3 Obsidian 知识库接入问题

**问题描述**：

Obsidian Vault 中有 2600+ 笔记，包含 Al Brooks 课程的完整知识。但这些知识无法直接发送给 LLM：
- 2600 篇笔记的总 token 数远超任何 LLM 的上下文窗口
- 简单全文搜索不够智能（关键词匹配 vs 语义理解）
- 笔记之间有复杂的链接关系（Obsidian 双链）

**解决方案**：构建向量检索服务，通过 MCP Tool 提供语义搜索。

```
构建阶段:
  Obsidian Notes → 文本提取 → 分块 (chunk) → Embedding 向量化 → 向量数据库 (如 ChromaDB)

检索阶段:
  CLAWDBOT 提问 "H2 信号在宽通道中的胜率是多少?"
       ↓
  MCP Tool: search_knowledge(query="H2 信号宽通道胜率")
       ↓
  向量检索 → 返回 Top-5 相关笔记片段
       ↓
  CLAWDBOT 基于检索结果 + 自身知识生成回答
```

**具体实施步骤**：
1. 使用 LangChain 或类似框架对 Obsidian Vault 进行索引
2. 选择 Embedding 模型（推荐 text-embedding-3-small 或 BGE-M3 支持中英混合）
3. 存储向量到 ChromaDB（轻量级，适合本地部署）
4. 在 MCP Server 中注册 `search_knowledge` Tool
5. 设置增量索引（新笔记自动入库）

### 5.5 交易状态管理缺失

**问题描述**：

交易是一个有状态的过程（观望 -> 计划 -> 入场 -> 持仓 -> 止盈/止损 -> 复盘），但 CLAWDBOT 本质上是无状态的——每次对话都是独立的。

这意味着：
- CLAWDBOT 不知道用户当前有没有持仓
- 无法在持仓过程中持续跟踪止损/止盈状态
- 无法在平仓后自动启动复盘流程

**解决方案**：在 api-service 中增加 `trade_session` 状态管理。

```python
# 交易会话状态机
class TradeSession:
    states = [
        "观望",       # 等待信号
        "计划中",     # 已识别机会，正在制定计划
        "待入场",     # 计划确认，等待入场点
        "持仓中",     # 已入场，跟踪中
        "已平仓",     # 已退出，等待复盘
        "复盘中",     # 正在复盘
    ]

# MCP Tools
get_trade_session()           # 获取当前会话状态
update_trade_session(state, data)  # 更新会话状态
```

**CLAWDBOT 行为变化**：

| 会话状态 | CLAWDBOT 行为 |
|----------|--------------|
| 观望 | 分析市场，寻找机会 |
| 计划中 | 审核交易计划，计算盈亏比 |
| 待入场 | 确认入场条件是否满足 |
| 持仓中 | 跟踪止损/止盈，提醒风险变化 |
| 已平仓 | 自动启动复盘提示 |
| 复盘中 | 对照 Al Brooks 原则分析交易 |

### 5.6 安全边界问题

**问题描述**：

SKILL.md 中的安全边界是通过提示词实现的（"绝不提供具体投资建议"、"每笔交易必须强调止损"），属于"软约束"。LLM 的 prompt-based 约束存在被绕过的可能性（prompt injection、jailbreak）。

**解决方案**：在 API 层面实施"硬约束"。

```
安全层级:

Level 1 (提示词层): SKILL.md 中的安全规则
  → 覆盖 99% 正常使用场景
  → 风险: 可被 prompt injection 绕过

Level 2 (MCP Server 层): 只暴露只读 Tools
  → CLAWDBOT 能调用 get_positions 但不能调用 place_order
  → 即使 prompt 被突破，也无法执行写操作

Level 3 (api-service 层): Token 权限控制
  → 为 CLAWDBOT 分配 read-only API Token
  → 所有写操作请求直接返回 403
```

**推荐 MCP Tools 权限矩阵**：

| Tool | 权限 | 说明 |
|------|------|------|
| analyze_market | 只读 | 获取数据并分析 |
| get_signals | 只读 | 获取信号检测结果 |
| get_positions | 只读 | 查看持仓状态 |
| search_knowledge | 只读 | 检索知识库 |
| check_setup | 只读 | 计算盈亏比（不执行） |
| update_journal | **写入** | 需要额外授权确认 |
| place_order | **禁止** | 不暴露给 CLAWDBOT |
| modify_stop | **禁止** | 不暴露给 CLAWDBOT |

### 5.7 Web Dashboard 策略匹配字段映射 Bug

**问题描述**：

Web Dashboard 的策略匹配页面显示"5 匹配策略"，但策略卡片的描述内容为空（显示 "..."）。

**根因分析**：

api-service 返回的策略数据结构中有两个字段：
- `description`: 简短描述（前端正在读取这个字段）
- `content`: 完整策略内容（实际数据在这里）

前端代码读取了 `description` 字段，但 api-service 对该字段返回空值，完整内容在 `content` 字段中。

**修复方案**：

```
选项 1: 前端修复
  将前端的字段映射从 strategy.description 改为 strategy.content

选项 2: 后端修复
  在 api-service 中确保 description 字段有值（如取 content 的前 200 字符）

推荐: 选项 1（前端修复），同时在后端补充 description 字段的默认值。
```

## 7. 结论与建议

### 7.1 核心发现

1. **现有系统基础扎实**：6 个微服务覆盖了数据采集、信号检测、交易管理的完整链路，api-service:8088 提供统一的 REST 接口，为 CLAWDBOT 接入提供了良好的基础。

2. **SKILL.md 需要大幅重构**：当前 17K tokens 的系统提示词过于臃肿，40%+ 内容与 references/ 目录重复。建议拆分为 ~7K tokens 核心提示词 + 按需加载的知识文件。

3. **MCP 协议是最佳集成方案**：相比 API 直连，MCP 提供了标准化接口、安全隔离、能力自动发现和双向通信的优势。推荐作为中期主力方案。

4. **CLAWDBOT 与 Telegram Bot 必须明确分工**：CLAWDBOT 负责深度分析与交互，现有 Telegram Bot 负责快速提醒。两者不应重叠。

5. **知识库接入是差异化能力**：2600+ 笔记的向量化检索将使 CLAWDBOT 具备独特的"Al Brooks 知识库"能力，这是其他通用 AI 助手无法比拟的。

6. **安全必须多层防御**：提示词层 + MCP 层 + API 层的三重安全机制，确保 CLAWDBOT 无法执行未授权的写操作。

7. **策略匹配页面存在 Bug**：Web Dashboard 的 `description` / `content` 字段映射错误需要修复。
