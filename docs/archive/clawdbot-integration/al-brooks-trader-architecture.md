## 1. 项目背景

### 1.1 当前痛点
- 现有Telegram Bot AI分析"很呆" - 只会报数字，缺乏价格行为洞察
- 缺少实时交易陪伴 - 无法在市场变化时及时提醒
- 没有系统化学习路径 - 无法结合用户进度给出针对性建议

### 1.2 目标愿景
构建**Al Brooks AI交易助手** - 一个基于价格行为学的智能交易导师，能够：
- 实时分析市场行情，识别价格行为模式
- 陪伴交易全过程（盘前→盘中→盘后）
- 提供个性化学习指导和错误复盘
- 与用户共同成长，持续进化

### 2.2 核心组件说明

#### 组件1：Al Brooks Skill（核心）
**职责**: 价格行为分析、交易指导、学习规划  
**能力**:
- Always In状态判断
- H1/H2/L1/L2回调识别
- 80%规则应用
- 交易者方程计算
- 支撑/阻力位分析
- 情绪状态评估

**知识来源**:
- Al Brooks 53课完整内容
- 用户交易历史
- 实时市场数据

#### 组件2：MCP Server（标准化接口）
**职责**: 统一AI与后端的交互协议  
**优势**:
- 标准化工具调用
- 安全凭据隔离
- 能力自动发现
- 双向实时通信

**提供的Tools**:
```typescript
{
  "analyze_market": "分析指定品种的价格行为",
  "check_setup": "审核交易计划的风险收益比",
  "get_signals": "获取当前信号检测结果",
  "fetch_history": "获取历史交易记录",
  "update_journal": "更新交易日记",
  "send_alert": "发送实时提醒通知"
}
```

#### 组件3：多模式协调器
**职责**: 根据场景切换AI工作模式

| 模式 | 触发条件 | AI行为 |
|------|---------|--------|
| **实时陪练** | 用户主动发起"开始交易" | 每分钟分析一次，主动推送建议 |
| **提醒模式** | 无人值守时 | 高概率信号出现时推送通知 |
| **复盘模式** | 交易结束后 | 分析当日交易，生成复盘报告 |
| **学习模式** | 用户询问课程 | 结合进度给出学习建议 |

## 3. 多模式详细设计

### 3.1 模式一：实时陪练模式

**触发**: 用户发送"开始实时分析 BTC 5分钟"  
**频率**: 每1-5分钟（根据K线周期）  
**流程**:

```
时间轴:
T+0s    ├─ AI读取最新K线数据
        ├─ 识别Always In状态
        ├─ 检测形态（通道/区间/突破）
        ├─ 寻找H1/H2/L1/L2信号
        ├─ 计算风险收益比
        └─ 生成分析报告 → 发送用户

T+60s   └─ 重复上述流程
```

**输出示例**:
```
【BTC 5分钟分析】
状态：上升通道（Always In Long）
形态：熊市骑行，预期最终下跌
信号：当前H2买入机会（双底确认）
建议：可在$43,200买入，止损$42,800(-0.9%)
目标：$44,000(+1.9%)，盈亏比2.1:1 ✅
⚠️  提醒：这是逆势形态的顺势交易，仓位减半
```

### 3.2 模式二：提醒模式

**触发**: 后端检测到高概率交易机会  
**条件**: 以下任一满足
- 出现H2/L2信号（置信度>70%）
- 价格触及关键支撑/阻力位
- 突破第二根K线确认
- 止损即将触发（距离<0.5%）

**推送内容**:
```
🚨 交易机会提醒

品种: BTC/USDT
时间: 2026-01-31 14:32
信号: H2买入（置信度78%）
价格: $43,250
建议: 查看完整分析请回复"分析BTC"
```

### 3.3 模式三：复盘模式

**触发**: 每日收盘后或用户发送"复盘今日"  
**分析内容**:
1. **交易统计**
   - 总盈亏、胜率、盈亏比
   - 最大单笔盈亏
   - R-multiple分布

2. **错误归因**
   - 违反规则交易占比
   - 情绪化交易占比
   - 技术误判占比

3. **改进建议**
   - 基于Al Brooks原则的反馈
   - 明日重点关注

**输出**: Markdown格式的复盘报告，自动保存到Obsidian

## 4. 集成方案对比

### 方案A：API直连（快速实现）

**架构**:
```
Clawdbot ──HTTP──→ api-service:8000 ──→ 后端数据
```

**优点**:
- 实现简单，1周内可用
- 无需额外基础设施

**缺点**:
- 安全凭据管理复杂
- 接口不统一，维护困难
- 无法服务端主动推送

### 方案B：MCP协议（推荐）

**架构**:
```
Clawdbot ←──MCP Protocol──→ MCP Server ──→ 后端数据
```

**优点**:
- 标准化接口，可扩展
- 安全隔离，凭据不外泄
- 能力自动发现
- 双向通信，支持推送

**缺点**:
- 需要开发MCP Server
- 2-3周实现周期

### 方案C：混合架构（最终形态）

**架构**:
```
                    ┌─→ 实时陪练（Clawdbot主动轮询）
用户 ──Telegram──┼─→ 提醒模式（MCP Server推送）
                    └─→ 复盘模式（定时任务触发）
```

**分工**:
- MCP Server：数据聚合、标准化接口
- Clawdbot：AI分析、自然语言交互
- telegram-service：消息收发

## 5. 数据流设计

### 5.1 实时分析数据流

```
1. 定时触发（每分钟）
   ↓
2. MCP Server.fetch_market_data(symbol, timeframe)
   ↓
3. 后端返回：价格、指标、原始信号
   ↓
4. Al Brooks Skill分析：
   - 计算HH/HL/LH/LL
   - 识别通道/区间
   - 检测H1/H2/L1/L2
   - 评估风险收益比
   ↓
5. 生成自然语言报告
   ↓
6. 发送给用户（Telegram/网页）
```

### 5.2 信号提醒数据流

```
1. 后端signal-service检测到高概率信号
   ↓
2. MCP Server接收信号事件
   ↓
3. Al Brooks Skill验证信号质量：
   - 检查80%规则
   - 确认Always In方向
   - 评估风险收益比
   ↓
4. 如通过验证，生成提醒文案
   ↓
5. 通过telegram-service推送用户
```

## 7. 关键问题记录

### Q1：Clawdbot vs 终端Kimi的差异
**问题**: 都是kimi-k2.5，为什么终端分析更透彻？  
**原因**: 
- 终端上下文连续，工具调用即时反馈
- Clawdbot有框架限制，工具调用有延迟

**解决方案**: 
- 复杂分析任务使用子代理
- 文档化项目结构，减少上下文依赖

### Q2：上下文限制如何处理？
**问题**: 写长代码会token不足  
**策略**:
- 模块化拆分，每模块<300行
- 文档先行，设计确认后再实现
- 复杂代码用终端生成，Clawdbot优化

### Q3：实时性如何保证？
**问题**: 5分钟K线需要每分钟分析  
**方案**:
- Clawdbot主动轮询（陪练模式）
- MCP Server主动推送（提醒模式）
- 用户手动触发（按需模式）
